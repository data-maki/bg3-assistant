## 2026-07-13 — Competitive-overlay product research

- **Status:** Proved; product recommendations documented.
- **Hypothesis:** The highest-value ideas from competitive overlays are not more persistent data, but phase-aware compression: preparation before a decision, one salient cue during it, and a short learning loop afterward. Applying those patterns to BG3 should reduce overlay text while improving Honor-specific readiness, route confidence, and recovery from dangerous state changes.
- **Experiment:** Compare current official feature sets and platform policies for leading Hearthstone, Valorant, Dota 2, and League of Legends overlays; identify the player job each feature performs; separate proven transferable patterns from competitive-game-specific clutter or prohibited information; then propose a prioritized BG3 overlay architecture with explicit affected areas and spacing.
- **Result:** Official product material showed four complementary jobs. Hearthstone Deck Tracker offloads known-card memory and, in Battlegrounds, converts board uncertainty into simulated win/tie/lethal risk. Valorant Tracker emphasizes map/mode-aware preparation and later performance trends, while Riot's current policy explicitly rejects opponent scouting and real-time prescriptions that alter immediate behavior. Valve's Dota Plus offers several item paths, recalculates after inventory deviations, gives level-specific ability choices, and defers failure explanation to a death summary and post-match comparison. Blitz, Porofessor, and Mobalytics combine pre-game setup, power-spike/state summaries, hotkey disclosure, configurable widgets, and post-match learning; Mobalytics itself warns the complete widget set can overwhelm and recommends using only what is needed. The repo now contains `COMPETITIVE_OVERLAY_RESEARCH.md` with a transfer matrix, three affected-state layouts, P0/P1/P2 roadmap, non-goals, and success measures. The best next product change is a deterministic `explore → preflight → dialogue/combat → recover` phase engine, compressed readiness with one blocker, hold-to-peek, a three-line combat pin, and a post-fight Stabilize card. The planner remains reference depth rather than the primary experience.
- **Reflection:** Competitive overlays are strongest when they shorten the distance between context and a decision, and weakest when they confuse more telemetry with more value. BG3 should borrow memory offload, adaptive alternatives, timed disclosure, and after-action learning—not player scouting, exact probabilities from incomplete state, automatic input, or continuous tactical direction. The pet can become substantially more useful while showing less by changing the question it answers in each phase.

## 2026-07-14 — Durable run and settings persistence

- **Hypothesis:** Restart resets are caused by split or unstable state authority between native `RunStore`, the embedded backend, and browser-local state. A single SQLite-backed native authority with one-time JSON migration and backend synchronization will preserve the entire run across packaged-app restarts without changing the player's confirmed progress.
- **Experiment:** Trace every startup/load/save path and installed data location; reproduce the reset against an isolated state directory; add failing persistence/migration tests; implement the smallest durable SQLite store for the full `HonorRun`; synchronize the backend/web projection without allowing it to overwrite native truth; then verify multiple challenges, party levels/builds, settings, and focus across two packaged-app restarts.
- **Result:** The reset was a split-authority bug: native used `run.json`, the embedded backend used a separate `run_state.json`, and the web map could merge stale localStorage state. Native and backend now share `state.sqlite3`. It stores the lossless `HonorRun`, one active-run pointer, the latest 20 transactional revisions per run, and persisted assistant settings; legacy `run.json` imports once when no SQLite run exists. Backend/web writes merge only their owned projection into the native snapshot, and web restore trusts the server database instead of unioning stale browser state.
